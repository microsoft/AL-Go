# Proposal: AL knowledge advice for issues and pull requests

An extension maintainer may need a Business Central rule before writing any code. The same question can arise later when reviewing a specific AL change. We propose an optional knowledge advisor for **both issues and pull requests in an AL-Go consumer repository**. It would use the official BCQuality `al-knowledge` skill and return cited advice as a workflow artifact. This document requests design feedback before adding workflow behavior to the templates.

## How it complements the PR reviewer

The [Copilot code reviewer](../CopilotCodeReview.md) uses BCQuality's review skill to produce findings on an eligible PR. The advisor answers a bounded platform question selected from the supplied context. An issue can use it independently of any PR or code review. On a PR the maintainer can use its advice alongside the review findings. The existing reviewer and its settings keep their current behavior.

For example, an issue might ask how a scheduled export should retrieve a credential when the app runs in several companies. The advisor can cite the applicable storage rule and explain why choosing company or module scope depends on whether companies share the account. On a PR that introduces an API-key field, it can point to the added field and recommend a concrete edit. A claim about the scheduled job's permissions still needs its own source or a check in the target environment.

## Proposed first implementation

- **Activation and cost.** Add separate repository-level opt-in, disabled by default. As an initial trigger, we suggest a maintainer-applied `knowledge-request` label on an open issue or eligible non-draft PR. Confirm the requester's current write or higher permission from GitHub. Apply the PR branch and author policy to the PR path. Limit each request to one selected question and one consultation; skip inference where policy disables the agent. Record the model and requested budget. Deduplicate repeat deliveries for the same request and input revision.
- **Input.** The trusted host retrieves the issue or PR from GitHub and validates repository and object identity. For an issue, supply a bounded snapshot of the report and relevant comments, recording its update time and content hash. For a PR, reuse the reviewer's trusted intake and base/head checks where applicable. Supply the relevant AL patch against the verified revision and recheck the head before accepting the result. Record unavailable or truncated evidence.
- **Plugin and permissions.** Use repository policy resolved by `ReadSettings`, the existing AL-Go `SetupBCQuality` action, and the filtered plugin root it returns. Require the knowledge entry point and action in that root. Keep marketplace credentials in the installation step. Use the reviewer's organization Copilot authorization model where supported. Generation can read the sanitized input and the prepared plugin and write only its designated report. Shell access, arbitrary URL retrieval, executing PR code, and GitHub write permissions are outside the model's tool surface.
- **Output.** Preserve the question, dispatch, original skill response, applicability, and canonical citations. Separate the technical recommendation and its next check from the host's validation and any unresolved project decisions. Produce an artifact only. A later decision about posting comments would need its own trusted publishing and deduplication design.

The [candidate advisor instructions](ALKnowledgeAdvisor.prompt.md) describe the model's role. Event authorization, filesystem isolation, read accounting and budgets belong to the host.

## What the pilots established

- For [AL-Go issue #2267](https://github.com/microsoft/AL-Go/issues/2267), the advisor returned `no-knowledge` on AS0054 and omitted an adjacent article about object name length. The external validator accepted the response. [Public run](https://github.com/javiarmesto/al-knowledge-advisor-smoke/actions/runs/41425467753)
- For [AL-Go issue #765](https://github.com/microsoft/AL-Go/issues/765), the advisor returned `partial` with two citations explaining runner isolation and test transactions. Whether the pipeline selects the runner per suite remained open. [Public run](https://github.com/javiarmesto/al-knowledge-advisor-smoke/actions/runs/41427034962)
- A separate private PTE pilot exercised real issue and PR events. The PR run identified the added credential field and validated three citations. The issue run validated five citations and left the cross-company scope decision open. Both consumed the filtered output of the official action. A first issue preflight separately exercised marketplace installation. To repeat the live cases with identical source, the pilot supplied an archive of reviewed Microsoft commit `a56b272c6b950c2a423bbeda190585cd53beca2a` to the action. It used a dedicated pilot credential and SDK harness. Organization authorization and template rollout still need upstream integration tests. [Public plugin handoff check](https://github.com/javiarmesto/al-knowledge-advisor-smoke/actions/runs/41439909193)
- Two observations shape the acceptance criteria: the first PR narrative issued a merge veto despite valid citations, and the issue summary initially overstated what the articles established about a background session. The PR wording has a regression check and prompt correction; a second live PR with that correction remains outstanding. Contract validation alone cannot catch all such errors. Review role boundaries and the preservation of uncertainty in both the advisor report and any summary.

## Release dependency and verification

The public `v1.9` tag inspected for this proposal (`ce45c5ab`) lacks the knowledge entry point; the pilot commit contains it even though both manifests say 1.9.0. Before shipping, identify a supported marketplace release with the entry point, action, response schema and consumer validator. An unavailable or policy-disabled skill should yield a diagnostic without consulting an unfiltered installation. The smoke repository and the pilot source override are development evidence, not proposed runtime dependencies.

For an implementation PR, extend settings defaults, schema and system-file generation for both PTE and AppSource templates. Add Pester coverage for opt-in, requester permissions, issue/PR discrimination, stale head, missing skill, filtered citations, empty selection and validator failures. Exercise an issue without a PR and a PR with a changed AL field in an AL-Go consumer. Verify clean skips when disabled, bounded cost on repeated events, complete read evidence before citation, and artifact-only behavior. Keep telemetry limited to outcome and counts, without issue bodies, prompts or credential values. Update the scenario guide and release notes when the feature becomes available.

**Decisions requested from maintainers:** Is a separately enabled, artifact-only advisor useful for both entry points? Is an explicit maintainer request the preferred initial trigger? Should the shared runner live alongside `ReviewAgent` or in a separate knowledge action that reuses its trusted preparation components?
